# Design

## Context

См. [proposal](proposal.md), Why. Существующая реализация изучена read-only; ниже реконструкция решений, не исходный проектный документ. Design нужен, поскольку фича пересекает GUI/Logic и использует внешнюю зависимость PySide6. Требования описаны в двух delta specs; Spec Kit остаётся исходным согласованным контрактом.

Explore установил: `Settings`, `Operation`, `Preview`, `ApplyResult` — frozen dataclasses в `tools/bootstrap.py`; `BootstrapError` несёт stage/message/field/path. `Bootstrapper.run()` объединяет последовательность преобразований. `BootstrapWindow` и `BootstrapWorker` находятся в `tools/bootstrap_gui.py`. Имеются Logic, CLI, GUI и layout-проверки; запись в них направлена в TemporaryDirectory. OpenSpec root — корень ITMOv2, а не вложенный lib-templater.

## Goals / Non-Goals

**Goals:** зафиксировать минимальное разделение ответственности и способ проверки согласованного Preview → подтверждение → Apply. Сохранить различие между наблюдаемым кодом и нормативным контрактом.

**Non-Goals:** новые слои services/controllers/repositories, общий файловый движок, diff содержимого, история, выбор другого корня, новые стили, отмена выполнения, транзакции/rollback, защита от внешнего редактирования, исправления CMake/C++/CI. Новые требования и повторная реализация исключены.

## Decisions

1. **API в существующем bootstrap.py, GUI отдельным адаптером.** Существующие Settings/Preview и BootstrapError связывают модули без Qt в Logic. Альтернатива — выделить новый пакет сервисов; для одной формы это лишнее расширение. CLI сохраняет свой parser/resolve_options и интерактивные вопросы.
2. **Preview моделирует последовательные изменения в памяти.** Наблюдаемые `_planned_text` и `_planned_kinds` позволяют последующим этапам читать будущий текст и учитывать rename/delete без записи. Альтернатива — старый dry-run; он пропускает записи и не моделирует будущие чтения. Временная копия на диске не нужна и противоречила бы ограничению Preview без записи. Operations — описание, не команды универсального исполнителя.
3. **Apply повторно использует преобразования с root/settings Preview.** Альтернатива — исполнять операции общим движком; контракт этого не требует. UI владеет подтверждением, актуальностью и однократностью попытки; Logic не вводит подтверждение для CLI. После попытки UI потребляет Preview, после отказа сохраняет его.
4. **Один QThread worker на вызов.** В коде есть сигналы succeeded/failed/finished, ссылки удерживаются до завершения, виджеты обновляет главный поток. Альтернатива — синхронный вызов в GUI-потоке; он блокировал бы обработку событий. На время работы поля/действия выключены, closeEvent откладывает закрытие; отмена worker не добавляется.
5. **Обычные Qt-виджеты и отдельные исходы.** QPlainTextEdit обеспечивает прокрутку, QMessageBox — явное подтверждение, подписи/Tab/фокус обслуживают клавиатуру. Альтернатива — дополнительные экраны или собственная item-model; они не нужны для текущего объёма. Ошибка Apply предупреждает о частичных изменениях, успех выводит сводку.

Состояния: initial → preparing → ready/empty/error; ready → confirming → ready при отказе либо applying при согласии; applying → result/error с обязательным новым Preview. Любое изменение параметров сбрасывает ready; preparing/applying блокируют повторные действия.

## Risks / Trade-offs

- Внешнее редактирование между Preview/Apply → контракт предполагает его отсутствие, новые проверки снимка не вводятся.
- Отказ файловой системы после Preview → остановка при первой ошибке, структурированная ошибка и предупреждение о частичных изменениях; атомарность не обещается.
- Уже настроенный проект может потерять обязательный шаблонный config → повторная настройка не гарантируется.
- Текущее поведение отличается от строгого сравнения с историческим bootstrap: API исключает служебные Spec Kit файлы, а тест сравнения нормализует старую цель в tests/CMakeLists.txt → сохранить исходные требования, отдельно отметить в Review; это не разрешение исправлять код или ослаблять контракт.
- Наличие тестовых методов не доказывает их успешный запуск → в этом эксперименте проверяются документы, тесты приложения не запускаются и runtime-приёмка не заявляется.

## Migration Plan

Миграция продукта и развёртывание отсутствуют. Реальный результат — только новый каталог change. Apply, Sync и Archive не выполняются; основные OpenSpec specs не создаются. Откат файловых действий продукта не проектируется: контракт его исключает. Задачи ниже остаются моделью возможной реализации и не запускаются этим экспериментом.
