# Рефлексия по Practice 5

В этой работе я использовал GitHub Spec Kit для разработки небольшого GUI, а OpenSpec попробовал отдельно, уже после реализации, чтобы сравнить подходы к работе с требованиями.

В ходе добавления фич в проект главным открытием для меня стал `constitution`, он явно определяет общие правила и границы проекта. Полезным оказалось и согласование двух независимых спецификаций. Без общего контракта UI и Logic могли бы по-разному понимать одни и те же действия.

Но для небольших проектов, которые я писал, мне всё же удобнее обычный `todo.md`. Когда знаешь структуру программы и представляешь, как внести изменения, не хочется проходить полный цикл спецификаций и планирования.

В проекте redis-valkey на C++ я веду такой список задач:

```
# TODO

Главная идея — соблюдать паттерны SOLID и GRASP.

Что главное нужно исправить:

- Database сейчас God-class, можно создать internal-class и делегировать методы, ну или другими методами исправить.

- Очень большая ошибка в выделении типов в Result: либо использовать полиморфизм, либо выделить классы для вывода, чтобы явно перегрузить с помощью Overload Pattern. (например, там явная ошибка GeoPositionResult — это можно объединить вместе с Array)

- Заменить std::variant для команд на полиморфные классы. Так явно лучше -> OCP

- Критически важно исправить GeoParser и обычный парсер на конечный автомат. Сейчас происходит какой-то хаос.
```

Я считаю, что для разработки в уже известной тебе области это явно легче. При работе с большим проектом OpenSpec / GitHub Spec Kit — незаменимые инструменты.

SDD я считаю полезным прежде всего там, где требования неоднозначны, участников несколько или сложно провести границы между компонентами. Согласованный контракт помогает заранее заметить, что участники понимают одну и ту же задачу по-разному.

Для небольшого знакомого проекта я по-прежнему скорее начну с `todo.md`. Если задача усложнится или её придётся разделить между независимыми командами, перейду к spec.
