# Feature Specification: Bootstrap UI — v1

**Feature Branch**: `practice_05` (существующая ветка)

**Created**: 2026-10-26

**Status**: Draft v1 — независимая UI-спецификация, ожидает приёмки человеком

**Input**: Графический интерфейс для ввода параметров bootstrap, предпросмотра файловых операций, подтверждения запуска и отображения результата. Ответственность UI Team в Practice 5.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Проверить изменения до запуска (Priority: P1)

Разработчик заполняет одну форму и просматривает будущие изменения файлов, прежде чем разрешить bootstrap менять проект.

**Why this priority**: Предпросмотр позволяет понять последствия выбранных параметров без изменения файлов.

**Independent Test**: Открыть форму, ввести допустимые параметры и получить предпросмотр. Проверить отображение всех предоставленных операций и отсутствие изменений в проекте.

**Acceptance Scenarios**:

1. **Given** приложение открыто, **When** пользователь ещё ничего не вводил, **Then** видны целевой каталог и значения по умолчанию, имя проекта пустое, область предпросмотра сообщает «Предпросмотр ещё не выполнен», запуск недоступен.
2. **Given** введено имя `demo_lib`, namespace оставлен пустым, остальные значения не менялись, **When** пользователь нажимает «Предпросмотр», **Then** виден статус подготовки, затем список операций для этих параметров; эффективный namespace показан как `demo_lib`; файлы проекта не изменяются.
3. **Given** предпросмотр получен, **When** пользователь просматривает список, **Then** у каждой операции видны действие и путь, а у переименования — исходный и конечный пути; длинный список доступен целиком через прокрутку.
4. **Given** имеется успешный предпросмотр, **When** изменяется любой параметр, **Then** предыдущий список перестаёт отображаться как актуальный, появляется требование повторить предпросмотр, запуск недоступен.
5. **Given** предпросмотр завершился без операций, **When** результат показан, **Then** виден текст «Нет изменений», запуск недоступен.

### User Story 2 - Подтвердить запуск и увидеть результат (Priority: P1)

Разработчик подтверждает применение просмотренных изменений и получает однозначный результат в том же окне.

**Why this priority**: Изменение файлов требует явного согласия и понятного завершения операции.

**Independent Test**: Начать с состояния с готовым непустым предпросмотром; отдельно проверить отмену подтверждения, подтверждённый успешный запуск и ошибку запуска.

**Acceptance Scenarios**:

1. **Given** готов актуальный непустой предпросмотр, **When** нажата кнопка «Запустить bootstrap», **Then** интерфейс запрашивает подтверждение, показывает целевой каталог и предупреждает о применении перечисленных файловых операций, включая удаления, если они есть.
2. **Given** открыто подтверждение, **When** пользователь выбирает «Отмена» или закрывает подтверждение, **Then** запуск не происходит, форма и предпросмотр сохраняются.
3. **Given** открыто подтверждение, **When** пользователь выбирает «Применить», **Then** начинается ровно один запуск с просмотренными параметрами; виден статус «Выполняется», изменение параметров, предпросмотр и повторный запуск недоступны.
4. **Given** запуск завершён успешно, **When** показан результат, **Then** видны сообщение об успехе и предоставленная сводка выполненных действий; форма снова доступна, прежний предпросмотр нельзя применить повторно без обновления.
5. **Given** запуск завершился ошибкой, **When** показан результат, **Then** видны сообщение об ошибке и доступное пояснение; сообщение об успехе отсутствует, параметры сохранены, перед повторным запуском требуется новый предпросмотр.

### User Story 3 - Исправить ошибку без потери ввода (Priority: P2)

Разработчик понимает, какое значение нужно исправить, и продолжает работу в той же форме.

**Why this priority**: Ошибка не должна заставлять повторно вводить все параметры или искать причину в терминале.

**Independent Test**: Ввести пустое и недопустимое имя, затем недопустимый namespace; проверить сообщения, исправление значений и возможность получить предпросмотр.

**Acceptance Scenarios**:

1. **Given** имя проекта пустое, содержит только пробелы либо равно `123-lib`, **When** нажата кнопка «Предпросмотр», **Then** рядом с полем показано правило допустимого имени, предпросмотр не начинается, запуск недоступен, остальные значения сохраняются.
2. **Given** имя допустимо, namespace равен `demo::`, **When** нажата кнопка «Предпросмотр», **Then** ошибка указана у namespace с примером `demo::lib`, запуск недоступен.
3. **Given** показаны ошибки полей, **When** значения исправлены и снова нажат «Предпросмотр», **Then** старые ошибки пересматриваются и не мешают допустимому вводу.
4. **Given** допустимые поля, **When** подготовка предпросмотра завершается ошибкой, например из-за неподходящей структуры проекта или недоступного файла, **Then** видны сообщение и доступная причина, параметры сохранены, запуск недоступен, предпросмотр можно запросить снова.

### Edge Cases

- Пустой namespace означает использование имени проекта; это значение явно показано перед подтверждением.
- Изменение параметра с последующим возвратом к прежнему значению всё равно требует нового предпросмотра.
- При подготовке предпросмотра повторные нажатия и изменение параметров недоступны; после завершения форма разблокируется.
- Длинные пути и сообщения доступны целиком через прокрутку или раскрытие, а тип операции различим без опоры только на цвет.
- После ошибки применения интерфейс не обещает, что файлы остались неизменными или были восстановлены; при отсутствии сведений о выполненных действиях сообщает, что состояние файлов требует проверки.
- Закрытие главного окна во время подготовки или применения не должно молча скрывать незавершённую операцию: интерфейс сообщает, что нужно дождаться результата. Отмена выполняющейся операции в v1 не предусмотрена.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Интерфейс MUST содержать одну основную форму: имя проекта, namespace, выбор стиля, флажки «Сохранить/создать bin» и «Сохранить/создать examples», кнопки «Предпросмотр» и «Запустить bootstrap», области операций и результата. Целевой каталог MUST быть явно виден и недоступен для редактирования в v1.
- **FR-002**: При открытии имя и namespace MUST быть пустыми, стиль — `google`, bin — включён, examples — выключен. Подсказка namespace MUST объяснять подстановку имени проекта. Режим EditorConfig MUST отображаться как «Соответствует выбранному стилю» без отдельного выбора.
- **FR-003**: Список стилей MUST содержать только `chromium`, `google`, `llvm`, `microsoft`, `mozilla`, `webkit`. Имя MUST начинаться с латинской буквы и далее содержать только латинские буквы, цифры и `_`. Непустой namespace MUST состоять из таких идентификаторов, разделённых `::`, причём каждый идентификатор может также начинаться с `_`.
- **FR-004**: Нажатие «Предпросмотр» MUST проверять поля; ошибки MUST указывать поле и правило исправления, сохранять весь ввод и не запускать подготовку при недопустимых значениях. Начальные и конечные пробелы MUST считаться недопустимыми, а не удаляться молча.
- **FR-005**: Успешный предпросмотр MUST показывать все предоставленные операции в доступном для полного просмотра списке: понятное действие над файлом или каталогом, путь, а для переименования — оба пути. Интерфейс MUST показывать параметры, к которым относится список. Предпросмотр MUST обходиться без изменения файлов проекта.
- **FR-006**: Запуск MUST быть доступен только после успешного непустого предпросмотра текущих параметров. Любое изменение параметра, ошибка предпросмотра или завершение применения MUST лишать прежний предпросмотр возможности запуска; пустой список MUST сопровождаться текстом «Нет изменений».
- **FR-007**: До применения интерфейс MUST запросить явное подтверждение с целевым каталогом и предупреждением о файловых изменениях. Отмена или закрытие подтверждения MUST возвращать к готовому предпросмотру без запуска. Подтверждение MUST относиться к параметрам и операциям, которые пользователь просмотрел.
- **FR-008**: Во время подготовки предпросмотра или применения интерфейс MUST показывать текущий этап, оставаться перерисовываемым и блокировать изменение формы и повторные действия. Один подтверждённый запуск MUST приводить не более чем к одному применению; закрытие окна MUST обрабатываться согласно Edge Cases.
- **FR-009**: По завершении интерфейс MUST разблокировать форму и показать успех либо ошибку с доступным пояснением и предоставленной сводкой действий. При ошибке MUST сохраняться параметры; неизвестные последствия MUST обозначаться как неизвестные, без обещаний отката.
- **FR-010**: Основные поля, кнопки и подтверждение MUST быть доступны с клавиатуры, иметь подписи и видимый фокус. Порядок Tab MUST следовать порядку полей и действий; нажатие Enter в поле ввода MUST не применять файловые изменения без подтверждения. При проверке ошибочного ввода фокус MUST переходить на первое ошибочное поле.

### Key Entities

- **Параметры формы**: Значения, заданные пользователем, и показанные эффективные значения, включая namespace и целевой каталог.
- **Предпросмотр**: Видимый список планируемых файловых операций, относящийся к текущим параметрам; может быть актуальным, отсутствующим либо требовать обновления.
- **Результат**: Видимый итог применения, пояснение ошибки при наличии и доступные сведения о выполненных действиях. Это понятия интерфейса, а не структуры общего контракта.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Основной сценарий для `demo_lib` проходит в одном основном окне: ввод → предпросмотр → подтверждение → результат, без ввода команд в терминале.
- **SC-002**: В 100% проверок предпросмотра, отмены подтверждения и ошибки ввода файлы проекта остаются неизменными.
- **SC-003**: Для каждого предоставленного в проверочном примере действия пользователь может прочитать тип и полный путь; для каждого переименования доступны оба полных пути, ни одна операция не пропущена.
- **SC-004**: Во всех сценариях изменения параметров, пустого предпросмотра и ошибки запуск недоступен до получения актуального непустого предпросмотра; повторное подтверждение не создаёт второго одновременного запуска.
- **SC-005**: При ручной приёмке проверяющий проходит основной сценарий только клавиатурой, исправляет каждый ошибочный пример из User Story 3 без повторного ввода остальных полей и различает успех, ошибку и выполнение по текстовым сообщениям.

## Assumptions

- Пользователь — разработчик, знакомый с назначением bootstrap. Все подписи, подсказки и статусы v1 — на русском; имена стилей и технические пути сохраняют исходное написание.
- Работа ведётся с текущим экземпляром шаблона. Выбор другого каталога, импорт/экспорт JSON, история запусков, редактирование списка операций, просмотр содержимого файлов и diff, отдельные настройки и отмена выполняющейся операции не входят в v1.
- Значения по умолчанию и правила допустимых полей взяты из существующего `tools/bootstrap.py`. Эта спецификация не расширяет семантику его параметров и не исправляет известные проблемы сборки.
- PySide6 задан пользователем и constitution как ограничение будущей реализации; выбор компонентов и внутренняя реализация Logic здесь не проектируются.
- UI ожидает возможность получить предпросмотр и результат применения, но формат обмена, сигнатуры, модели ошибок и способ запуска не определяются. Зависимость от этих возможностей подлежит согласованию человеком после независимых спецификаций.
- UI v1 описывает желаемое наблюдаемое поведение. Вопросы ниже не означают, что Logic уже обеспечивает необходимые гарантии, и не образуют общий контракт. До реализации требуется приёмка обеих спецификаций и согласование человеком.

### Вопросы к Logic Team для последующего согласования

1. Какие сведения фактически доступны о планируемых операциях: действие, файл или каталог, исходный и конечный пути? Можно ли получить полный предпросмотр без изменения файлов?
2. Как сообщаются ошибки проверки, подготовки и применения; какие сведения о частично выполненных действиях доступны после ошибки?
3. Какие гарантии возможны, если файлы проекта изменились между предпросмотром и подтверждением? Как пользователь узнает, что просмотренный список больше не соответствует состоянию проекта?
