## Summary

Одна форма PySide6 вызывает независимый API `preview(root, settings)`, показывает операции, запрашивает подтверждение и передаёт полученный Preview в `apply(preview)`. Результат и ошибки отображаются в том же окне. Существующий CLI, вопросы, JSON и `--dry-run` сохраняются. План охватывает обе спецификации; документы находятся только в `specs/002-bootstrap-logic/`.

Дополнительные экраны, параметры, транзакции, откаты, универсальный файловый движок и несвязанный рефакторинг не входят в реализацию.

## Technical Context

**Language/Version**: Python 3.12 — выбранная среда реализации и демонстрации; C++ и его настройки не меняются.

**Primary Dependencies**: только PySide6 для GUI. Logic/CLI используют стандартную библиотеку. При реализации закрепить проверенную версию PySide6 в `requirements-gui.txt`; дополнительных Python-зависимостей не требуется.

**Storage**: файлы текущего шаблона; Preview и состояние формы только в памяти, без истории и сохранения настроек.

**Testing**: `unittest`, `tempfile`, `subprocess`, `unittest.mock`; GUI — настоящий QApplication и `PySide6.QtTest`. Существующие GoogleTest/CTest и `sh scripts/check.sh` сохраняются.

**Target Platform**: Windows для desktop-демонстрации; Linux/WSL для имеющейся shell-проверки. Logic переносима; Qt offscreen допустим для автоматизации, ручная демонстрация выполняется с дисплеем.

**Project Type**: desktop-приложение к Python bootstrap C++ шаблона.

**Performance Goals**: GUI принимает события во время Preview/Apply; числовых SLA и пооперационного прогресса нет.

**Constraints**: Preview не пишет даже временные файлы; Apply останавливается при первой ошибке, возможны частичные изменения. Между Preview и Apply предполагается отсутствие внешнего редактирования.

**Scale/Scope**: одно окно, один текущий шаблон, один выполняющийся вызов Logic. Корень виден, но недоступен для редактирования.

## Phase 1 — Design

### Logic и последовательный Preview

- Сохранить Options, Bootstrapper, пресеты, тексты заготовок, набор текстовых файлов и исключения. В том же модуле добавить данные и два вызова из [binding](contracts/bootstrap-api.md).
- Preview проверяет значения без trim, подставляет имя вместо пустого namespace и проверяет четыре обязательных файла. Затем выполняет существующие этапы в режиме планирования без записи/печати.
- Нынешний dry-run недостаточен: после пропущенной записи следующий этап читает исходный файл. Внутри Bootstrapper нужны локальные таблицы будущего текста и существования затронутых путей. Только чтения, обход и файловые действия существующих этапов направить через минимальные вспомогательные методы. Ранее созданные текстовые файлы участвуют в последующих заменах.
- Это локальное сопровождение bootstrap, без публичного виртуального filesystem, универсальных команд и временной копии на диске. При необходимости фиксировать порядок обхода для нового API, сохраняя прежний CLI dry-run.
- Порядок этапов: clang-format → EditorConfig → gitignore → замены текста → tests/CMakeLists → переименования → bin → examples. Создание родителей отражается до создания файлов. Безусловные перезаписи сохраняются; повторные update одного пути допустимы. Delete каталога включает содержимое.
- Apply использует root/settings Preview и существующие преобразования с реальной записью. Список operations служит описанием, а не программой универсального исполнителя. Первый сбой прекращает выполнение; успех возвращает краткую сводку.
- CLI сохраняет parser, resolve_options, вопросы и main как свой адаптер. API не вызывает input/print/sys.exit. Отделить печать сводки от общих этапов, сохранив CLI-вывод. Ошибки конфигурации и filesystem доступны как структурированные исключения.

### Одна форма

- QWidget с подписанными полями, шестью стилями, двумя флажками, двумя кнопками, неизменяемым root, эффективными настройками, прокруткой списка операций и результата. Русские подписи и defaults по UI v2.
- Обычные виджеты; собственный item-model не нужен. Для rename видны оба пути; действие и файл/каталог различаются текстом.
- Окно хранит единственный Preview. Любое изменение поля сбрасывает возможность Apply, даже после возврата прежнего значения. Отказ в QMessageBox сохраняет Preview; любой начатый Apply его потребляет.
- Один небольшой QThread worker на вызов Preview либо Apply: работа в run(), результат/ошибка передаются сигналами в GUI-поток. Слоты виджетов выполняются в главном потоке. Ссылки на worker хранятся до finished, затем освобождаются. Отдельный worker framework не нужен.
- При работе поля и действия заблокированы, статус «Подготовка»/«Выполняется». Закрытие окна откладывается до finished; отмены операции нет.
- Подтверждение показывает root и предупреждение, включая удаления. Отмена безопасна по умолчанию. Enter в поле не применяет изменения; Tab, подписи и фокус на первом ошибочном поле обязательны.
- После ошибки Apply показать предупреждение о возможных частичных изменениях и необходимости проверить файлы; успех не показывать. После результата форма доступна, требуется новый Preview.

### Последовательность реализации и проверки

1. Сначала проверки параметров, неизменности и последовательности Preview; показать ожидаемое падение из-за отсутствующего API. Затем минимально добавить API.
2. Проверить Apply на отдельных копиях, равенство исходному CLI для четырёх сочетаний bin/examples, остановку/ошибки чтения, декодирования, записи, rename/delete. Поведение CLI зафиксировать до изменения общих этапов.
3. Добавить форму/worker и сквозные проверки настоящего GUI: demo_lib, неверный параметр, отказ без Apply/записи. Проверить устаревание/пустой Preview, блокировки, результат/ошибку, закрытие и клавиатуру.
4. Выполнить Logic/CLI без Qt, затем GUI-набор с Qt и прежний `sh scripts/check.sh`. Подробности — в [quickstart](quickstart.md).

Для изменений A/B обязателен test-first по AGENTS.md; план их не меняет. Новые тесты проверяют контракт и файловые эффекты, не копируют внутреннее устройство таблиц Preview.
