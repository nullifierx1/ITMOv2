# Research: единая реализация Practice 5

Дата: 2026-10-26. Источники требований: обе спецификации v2, `specs/contract.md`, constitution. Локальные источники: `tools/bootstrap.py`, `tests/bootstrap_layout_test.py`, `tests/CMakeLists.txt`, `tests/foo_ut.cpp`, `scripts/check.sh`, README, style-guide и файлы форматирования.

## 1. Граница модулей

**Decision**: оставить независимый Python API и существующие преобразования в `tools/bootstrap.py`; единственное новое приложение — `tools/bootstrap_gui.py`.

**Rationale**: исходный модуль уже содержит Options, Bootstrapper и проверки. Импорт не вызывает main. Пустой GUI namespace нормализуется при Preview; CLI продолжает использовать resolve_options со своими правилами.

**Alternatives considered**: отдельные services/models/controllers и перенос CLI в новый пакет увеличивают diff; subprocess с разбором печати не даёт надёжного контракта ошибок и Preview.

## 2. Точный Preview без записи

**Decision**: использовать существующие этапы с локальным промежуточным состоянием текста и путей в памяти. Общие чтения/действия Bootstrapper учитывают это состояние только в новом режиме Preview. Apply выполняет существующие преобразования на диске.

**Rationale**: dry_run подавляет запись, после чего последующие этапы читают старое содержимое. Это существенно для tests/CMakeLists и последовательной настройки bin/examples в корневом CMake. Также новые `.clang-format`, `.editorconfig`, `.gitignore` могут участвовать в последующих заменах. Preview должен видеть результат предыдущего этапа, отражать создание родителей, rename и удаление каталогов. После rename учитывать новые пути; тип create/update определяется состоянием перед текущим действием.

Не объединять повторные записи одного файла: список описывает последовательность, включая безусловные перезаписи. Стабильный порядок обхода для нового API допустим как внутренняя деталь; нельзя незаметно менять legacy dry-run. Точный состав проверяется относительно исходного CLI на копиях.

**Alternatives considered**: нынешний dry-run недостаточно точен; копирование на диск ради Preview нарушает выбранное ограничение отсутствия записи; отдельный дублирующий генератор создаёт расхождение; универсальная файловая машина избыточна.

## 3. Сохранение CLI и особенностей генератора

**Decision**: сохранить parser, resolve_options, интерактивные вопросы, JSON coercion, приоритеты, dry-run, обычный запуск без подтверждения и печатную сводку. API работает без ввода, печати и SystemExit; ошибки передаются данными исключения.

**Rationale**: CLI уже выполняет требуемые преобразования в заданном порядке. В частности, исправление tests/CMakeLists следует после замен, а заготовки bin/examples записываются после замен. Эти особенности сохраняются, даже если выглядят спорно. Пустой JSON namespace по-прежнему ошибочен; GUI-подстановка не переносится в resolve_options.

**Alternatives considered**: направить прежний CLI через новый Preview/Apply — лишнее изменение его dry-run и вопросов; исправить заодно CMake/заготовки/исключения — выход за scope.

## 4. Отзывчивость GUI

**Decision**: небольшой наследник QThread выполняет один вызов Logic в run() и передаёт результат/ошибку сигналом. Окно обновляется только в главном потоке, хранит worker до finished и откладывает закрытие до завершения. Рабочие slots в наследник QThread не добавляются.

**Rationale**: Qt документирует наследование QThread и сигналы результата; объект QThread сам принадлежит создавшему потоку, поэтому его slots не подходят для переноса работы. См. [официальную документацию Qt for Python: QThread](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html).

**Alternatives considered**: QObject.moveToThread также поддержан Qt, но здесь требует дополнительных связей жизненного цикла; синхронный вызов блокирует форму; процесс, пул задач и асинхронный framework не нужны.

## 5. Данные и ошибки

**Decision**: небольшие frozen dataclass для настроек, операции, Preview и успеха; одно исключение BootstrapError с stage/message/field/path. Последовательность операций неизменяемая. Данные не сохраняются в JSON и не получают version/id/token.

**Rationale**: достаточно для Python UI ↔ Logic. UI хранит сам Preview и отвечает за его актуальность/однократный запуск. Нет необходимости строить серверную машину состояний или журнал выполненных операций.

**Alternatives considered**: Result hierarchy, универсальные envelopes, сериализация, generation IDs, транзакционный журнал и механизм отката не требуются контрактом.

## 6. Проверка и окружение

**Decision**: unittest и стандартная библиотека для Logic/CLI; QApplication/QtTest для настоящего GUI. Python 3.12 выбран для будущего прогона; PySide6 — единственная новая зависимость, версия фиксируется после проверки установки. Существующий shell-check не расширяется до GUI-runner.

**Rationale**: отдельный прогон без установленного Qt доказывает независимость Logic. Копии шаблона позволяют безопасно проверить запись. Сравнение с исходным CLI для четырёх комбинаций защищает поведение лучше проверки отдельных файлов. scripts/check.sh использует Ninja, CTest и `/usr/bin/python3`, поэтому его воспроизводимая среда — Linux/WSL.

**Alternatives considered**: pytest/pytest-qt, новый CI pipeline и изменение CMake для Python-тестов увеличивают зависимости и scope.

## Итог Phase 0

Все вопросы проектирования разрешены решениями выше. Технических блокирующих уточнений нет. Приёмка документов человеком и фиксация фактически проверенного GUI-окружения остаются следующими организационными шагами, не меняющими контракт.
