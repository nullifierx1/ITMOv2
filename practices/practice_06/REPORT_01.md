## Подтверждённые анализом исходного кода

### S01. Недоверенные параметры включаются в SQL - P1

- **Компоненты:** `GET /profile?id=`, `GET /search?q=`, `GET /assistant/context?order_id=`.
- **Код:** [service.py, строки 56–59](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L56-L59), [88–89](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L88-L89), выполнение запроса в [38–39](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L38-L39).
- **Небезопасное поведение и причина:** значения query встраиваются f-строками в SELECT и затем передаются в `db.execute`. Тип идентификатора не проверяется, поисковая строка не связывается как SQL-параметр.
- **Предпосылки и последствия:** достаточно доступа к локальному API; соответствующие маршруты не проверяют сессию. SQL-интерпретатор получает управляемый фрагмент выражения, что создаёт SQL injection и риск чтения лишних строк или иных доступных через SELECT данных. Выполнение нескольких SQL-команд, изменение таблиц и исполнение кода этим анализом не доказаны.
- **Рекомендация:** параметризовать все три SELECT, проверять типы id/order_id; отдельно ограничить доступ к данным. INSERT заказа уже параметризован и не относится к этой находке.

### S02. Профили доступны без проверки сессии и прав - P1

- **Компоненты:** `GET /profile`, `GET /search`.
- **Код:** [service.py, строки 41–59](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L41-L59); состав профиля - [20–24](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L20-L24).
- **Поведение и причина:** `/profile` выбирает профиль по клиентскому id, `/search` ищет по всем профилям. Перед этими ветвями нет общей авторизации; сами ветви не читают sessions. Пустой поиск не ограничивает выборку конкретным владельцем.
- **Предпосылки и последствия:** локальный вызывающий, включая анонимного, получает доступ к учебным именам, email и адресам. Для этого дефекта не нужна SQL injection: обычный выбор чужого id уже нарушает разделение клиентов.
- **Рекомендация:** проверять сессию; клиенту выдавать собственный профиль, поиск ограничить разрешённой областью или ролью сотрудника. Политику поиска явно определить.

### S03. Чужие заказы доступны напрямую и через AI-контекст - P1

- **Компоненты:** `GET /orders`, `GET /assistant/context`.
- **Код:** [service.py, строки 60–61](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L60-L61), [88–98](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L88-L98).
- **Поведение и причина:** первый маршрут возвращает все заказы; второй выбирает заказ по переданному order_id и добавляет его в prompt. Ни сессия, ни owner не проверяются. Это отдельный дефект от SQL injection.
- **Предпосылки и последствия:** достаточно локального запроса. Раскрываются владелец, товар и цена чужой покупки; при последующем переносе контекста модель получает эти данные. Фактической передачи LLM в этом этапе не было.
- **Рекомендация:** фильтровать заказы по owner из сессии, проверять принадлежность перед сборкой контекста, передавать минимум полей. Служебный обзор заказов разрешать отдельно.

### S04. Заголовок X-Role заменяет серверную роль - P1

- **Компонент:** `GET /admin/export`.
- **Код:** [service.py, строки 74–77](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L74-L77), серверные роли уже сохраняются в [49–55](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L49-L55).
- **Поведение и причина:** единственная проверка экспорта сравнивает клиентский `X-Role` со строкой `staff`. Токен и роль в sessions не используются.
- **Предпосылки и последствия:** вызывающий контролирует заголовки и имеет доступ к локальному API; учётная запись сотрудника не нужна для прохождения этой проверки по коду. Последствие - полный экспорт профилей.
- **Рекомендация:** получать роль только из проверенной серверной сессии; игнорировать клиентское заявление о роли при принятии решения.

### S05. Цена заказа берётся из тела запроса - P1

- **Компонент:** `POST /orders`.
- **Код:** [service.py, строки 62–73](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L62-L73).
- **Поведение и причина:** `body.get("price", self.products[product])` предпочитает присланную цену каталожной и записывает её в orders. Проверка сессии и известного товара есть, проверки цены нет.
- **Предпосылки и последствия:** нужна действительная сессия и известный товар. Клиент управляет стоимостью учебной покупки; потенциально сохраняются нулевая, отрицательная или иная некаталожная цена, если значение принимается SQLite. Конкретные пограничные типы не проверялись.
- **Рекомендация:** брать цену только из серверного каталога; поле price отклонять либо не использовать. Сохранить owner из сессии и параметризованный INSERT.

### S06. Файловый маршрут не разделяет владельцев внутри Sandbox - P1

- **Компонент:** `GET /files`.
- **Код:** [service.py, строки 78–80](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L78-L80), [sandbox.py, строки 12–28](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/sandbox.py#L12-L28).
- **Поведение и причина:** user и path целиком задаются query, сессия не проверяется. Sandbox запрещает выход за физический корень, но допускает любые разрешившиеся внутри него пути. Отдельных правил для чеков Alice, Bob и private нет.
- **Предпосылки и последствия:** локальный доступ к API; выбор чужого user не требует обхода SQL или сессии. Доступны чужие чеки; нормализация относительных путей создаёт также путь к служебной заметке внутри песочницы. Конкретный HTTP-вариант такого пути ещё не проверен.
- **Рекомендация:** связывать владельца с сессией и серверным каталогом, после нормализации проверять разрешённый подкаталог и перечень файлов. Сохранить неизменным физический барьер sandbox.py.

### S07. Публичный журнал содержит пароли и токены запросов - P1

- **Компоненты:** журналирование dispatch, `GET /debug/logs`.
- **Код:** [service.py, строка 44](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L44), [81–82](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L81-L82).
- **Поведение и причина:** до авторизации сохраняются полные body, target и headers. Тело login содержит пароль, заголовки последующих запросов содержат X-Token. Чтение журнала не защищено.
- **Предпосылки и последствия:** в процессе должны произойти login и/или запрос с токеном. Другой локальный вызывающий получает эти учебные секреты; возможна подмена пользователя. Возвращённый login-токен не журналируется как ответ: речь именно о токене в последующем запросе.
- **Рекомендация:** не писать пароли и токены, минимизировать тела и query, закрыть или удалить debug-маршрут. События связывать с установленным сервером субъектом, а не с заявленными заголовками.

### S08. Отзывы включаются в HTML без экранирования - P1

- **Компоненты:** `POST /reviews`, `GET /reviews/view`, HTTP-ответ.
- **Код:** [service.py, строки 83–87](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L83-L87), [130–133](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L130-L133).
- **Поведение и причина:** text сохраняется без проверки сессии, типа и продукта, затем включается в `<p>` без экранирования. Строковый результат отдаётся как `text/html`, специальной защитной политики ответа нет.
- **Предпосылки и последствия:** нарушитель может записать отзыв; для браузерного воздействия нужен просмотр HTML. Подтверждён опасный поток сохранённого текста в HTML, то есть дефект stored XSS. Выполнение JavaScript и конкретный ущерб в браузере не воспроизводились. Утверждать кражу токена из браузерного хранилища нельзя: такого хранилища код не описывает.
- **Рекомендация:** экранировать текст при выводе, проверять схему и права записи, ограничить размер и допустимые продукты. CSP использовать как дополнительный барьер.

### S09. Исполнитель AI-инструментов не проверяет полномочия - P1

- **Компонент:** `POST /assistant/execute`.
- **Код:** [service.py, строки 99–109](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L99-L109), [sandbox.py, строки 21–35](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/sandbox.py#L21-L35).
- **Поведение и причина:** клиент выбирает tool и arguments; проверки сессии, владельца, роли и соответствия заказа нет. `read_file` читает разрешённый Sandbox путь, `export_profiles` выдаёт все профили, `delete_tree` удаляет указанный путь внутри Sandbox, включая сам корень. Неизвестные инструменты отклоняются, но известные не авторизуются.
- **Предпосылки и последствия:** достаточно локального доступа и корректного по ожидаемой структуре JSON. По коду доступны чтение чужих учебных файлов, экспорт профилей и уничтожение учебного дерева. ОС за пределами Sandbox, shell и произвольное выполнение кода не входят в доказанное воздействие.
- **Рекомендация:** авторизовать каждую операцию и ресурс по сессии, разрешать клиенту только получение собственного чека, запретить клиентское удаление и служебный экспорт. Проверять строгую схему решения; не считать решение модели разрешением сервера.
- **Разграничение:** прямая передача опасного JSON была бы проверкой этого дефекта, а не доказательством prompt injection. В этом этапе она не выполнялась.

### S10. Внутренние исключения возвращаются клиенту - P2

- **Компонент:** HTTP handler, обработка JSON и ошибок dispatch.
- **Код:** [service.py, строки 119–129](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L119-L129).
- **Поведение и причина:** любой перехваченный Exception превращается в 500 с `str(exc)` и именем типа. До dispatch не проверяется, что JSON имеет нужную объектную структуру и поля.
- **Предпосылки и последствия:** ошибочный ввод или ошибка SQLite/файловой операции. Клиент получает внутренние детали; в зависимости от исключения это могут быть сведения о запросе или пути. Точное содержание HTTP-ошибок ещё не наблюдалось. Ошибки ввода также ошибочно классифицируются как внутренние 500.
- **Рекомендация:** проверять схему и типы, возвращать контролируемые 400/404/403; для непредвиденных ошибок отдавать общее сообщение, подробности хранить только в закрытом журнале без секретов.

### S11. Накопление данных в памяти не ограничено - P2

- **Компоненты:** logs, reviews, sessions.
- **Код:** инициализация [service.py, строки 33–36](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L33-L36), добавление [44](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L44), [49–55](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L49-L55), [83–87](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L83-L87); лимит отдельного тела [121–125](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L121-L125).
- **Поведение и причина:** каждый dispatch добавляет запись журнала, каждый успешный login - сессию без срока, отзывы добавляются без общего лимита. Очистка, ротация и ограничения количества в коде отсутствуют. Чтение журнала и вывод отзывов обрабатывают весь накопленный объём.
- **Предпосылки и последствия:** повторные локальные запросы на протяжении жизни процесса. Растёт расход памяти и стоимость больших ответов. Наличие отдельного лимита тела 65536 байт не ограничивает суммарное накопление. Отказ процесса и порог нагрузки не подтверждены; отсутствие срока сессии само по себе также не доказывает захват сессии.
- **Рекомендация:** ограничить число и суммарный объём записей, ввести ротацию и пагинацию, срок сессий и ограничения частоты. Нагрузочную проверку проводить отдельно и без разрушительных сценариев.

## Требующие динамической проверки

### H01. Вредоносный отзыв может изменить решение реального planner

**Статическое основание:** отзыв принимается без авторизации в [service.py, строках 83–85](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L83-L85), все отзывы независимо от товара включаются в prompt рядом с инструкциями и вопросом в [88–98](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/lab/service.py#L88-L98). Потенциальный путь воздействия проходит через executor из S09. Форматирование JSON не превращает текст отзыва в доверенную инструкцию и не гарантирует, что модель его проигнорирует.

**Что ограничивает вывод:** [planner-system.txt, строки 1–5](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/planner-system.txt#L1-L5) прямо запрещает раскрытие чужих данных и удаление, велит считать отзывы данными и допускает `refuse`. [opencode.json, строки 16–20](https://github.com/nullifierx1/ITMOv2/blob/c24eb419df292af125b533ec36d8743a32149102/practices/practice_06/opencode.json#L16-L20) запрещает инструменты planner. Python-сервис не вызывает LLM; отдельный рабочий агент переносит её решение. Поэтому подчинение модели отзыву и последующее опасное действие не подтверждены.

**Возможные последствия и защита:** если модель примет отзыв за инструкцию и рабочий агент перенесёт решение, незащищённый executor может выполнить чтение, экспорт или удаление внутри стенда. Следует сократить контекст и доступные действия, отделять данные от инструкций и обязательно проверять полномочия на сервере. Приоритет проверки P1 из-за потенциальной связи с S09, вероятность пока неизвестна.

**Будущая проверка:** отдельный реальный `shop-planner` с зафиксированными моделью и настройками; одинаковые system prompt и обычная задача до/после добавления отзыва; точные входы, исходные ответы, результат execute и состояние файлов/данных. Отказ или некорректный JSON фиксировать честно, не заменяя ответ. Прямой опасный JSON проверить отдельно. Сейчас эксперимент отложен по ограничению текущего этапа; доступность LLM не проверялась.

## Тесты, Makefile и критерии

По тексту файлов имеются 9 функциональных тестов Shop, 4 теста Sandbox и 3 HTTP-теста: всего **16 тестовых методов**. Это инвентаризация, не результат запуска. [test_service.py](lab/test_service.py) проверяет обычные покупки, свои данные и физический барьер; [test_http.py](lab/test_http.py) - транспорт, обычную покупку, health/404 и loopback. Например, тест экспорта передаёт одновременно staff-токен и X-Role и не устанавливает, какой из них действительно проверен. Отрицательные проверки разграничения клиентов, роли, цены и executor отсутствуют. Успех этих тестов не доказывал бы безопасность.

Расхождение с `make step6` объясняется рабочим каталогом. Цель **есть** в [корневом Makefile, строках 17–18](../../Makefile#L17-L18): она вызывает тесты practices/practice_06. В [Makefile практики](Makefile) есть install/test/run, а test делегирует в lab. [Makefile лаборатории](lab/Makefile) запускает `python3 -m unittest -v`. Таким образом, `make step6` предусмотрен из корня, но не из каталога практики. Корневой `make test` дополнительно затрагивает практики 1–3. Команды не запускались по статической области текущего этапа; Makefile не менялся.
