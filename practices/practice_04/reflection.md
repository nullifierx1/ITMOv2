# Reflection

В `AGENTS.md` полезнее всего оказался заранее зафиксированный scope. Я видел, что цель практики ограничена Feature A и Feature B, поэтому не стал заодно исправлять `BUILD_BIN`, расхождение C++ standard или CI: это явно отмечено как OUT OF SCOPE. Такие ограничения помогли не превратить небольшую работу в переписывание всего шаблона.

TDD skill дал понятный порядок действий. Для Feature A сначала был подтверждён RED: `tests/CMakeLists.txt` ссылался на отсутствующий `test_foo.cpp`. Затем был сделан минимальный GREEN — ссылка на `foo_ut.cpp` и один smoke test. Для Feature B сначала появился тест bootstrap layout, который проверял итоговую структуру, и только после этого header был перенесён в `include/__PROJECT_NAME__/`.

MCP оказался полезен как отдельный источник проверки, а не как замена тестам. Context7 использовался для реальной документации, в том числе по GoogleTest, CMake и OpenCode V2. Собственный `template-inspector` позволил проверить layout шаблона через отдельный read-only tool; вызов с `../bad` вернул понятную ошибку и не остановил сервер.

Verification hook показал ценность автоматической обратной связи после изменения файлов. Он запускал проверку после file-changing tool; отдельно были показаны FAIL с `EXPECT_TRUE(false)` и PASS после возврата `EXPECT_TRUE(true)`. Это не отменяет финальную проверку, но помогает заметить проблему ближе к моменту изменения.

Самым неудобным оказался Windows environment. `sh` не находился в PATH, WSL был недоступен, поэтому финальную проверку пришлось выполнить эквивалентом runner нативными Windows-командами: CMake configure, build, CTest и Python 3.12 для bootstrap-теста.

В итоге правила, skill, MCP и hook полезны не сами по себе. Они уменьшают вероятность случайно изменить лишний код и дают воспроизводимую проверку того, что результат действительно работает.

## Ready skill analysis

Skill заставляет сначала доказать проблему тестом, а не считать её очевидной по коду. Он требует убедиться, что RED падает именно из-за нужного дефекта, а не из-за опечатки или сломанной среды. GREEN должен быть минимальным, чтобы исправление было связано с проверяемым поведением. В этой практике такой порядок реально помог и для Feature A, и для Feature B.
